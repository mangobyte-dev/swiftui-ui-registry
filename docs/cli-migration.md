# Swift CLI migration contract

Stage status and phase evidence live in `docs/component-roadmap.md`, Stage 6. This document records the implementation choices and compatibility boundaries for the rewrite

## Running from a clone

```sh
swift run swiftui-registry validate
swift run swiftui-registry search nutrition dashboard --kind block --platform iOS --target-version 26.0
swift run swiftui-registry install button --destination Sources/Feature/Components --plan
swift run swiftui-registry preset decode a13GkaOXWwIF
swift build -c release
```

Consumer commands accept `--registry /absolute/path/to/clone` after the command name. Without it, the local source searches the working directory and its ancestors for `Registry/registry.json`. Release snapshot resolution and Homebrew distribution belong to Phase D

## Package boundaries

`RegistryKit` has no dependency on `SwiftUIRegistryFoundations` and imports no SwiftUI. It owns loading, structural validation, resolution, receipts, source comparison, installation, search, and preset behavior. The executable owns argument parsing and output. The existing foundation target and its source remain design tokens only

The three direct dependencies are `swift-argument-parser` for the real parser exercised by command tests, `swift-dependencies` for replaceable effects, and `swift-snapshot-testing` for inline output and directory snapshots. Their resolved transitive packages are recorded in `Package.resolved`; there are no other direct package dependencies. The pattern was measured from `pointfreeco/pfw` at 854b491

Filesystem access, registry selection, console output, UUID generation, and the git merge adapter are dependencies. Tests supply an in-memory filesystem and registry source. The merge integration test selects the live git adapter deliberately. No command records a timestamp or waits on a timer, so the clock supplied by swift-dependencies has no Phase A consumer; cache timing in Phase D must use the injected clock

The Showcase retains its codec in Phase A. Its tuning model contains app-only environment switches and remembered color state; importing the entire consumer tool engine only for the codec would couple that private model to installer dependencies. RegistryKit and the unchanged Showcase continue to consume the same pinned vector contract. The Swift test resource is byte-checked against `Tests/RegistryTests/preset_vectors.json`

## Parity boundaries

Owned source, receipt JSON, bases, conflict artifacts, search JSON, and preset theme files preserve Python bytes. The temporary parity script compares exit status and both output streams. Its directory comparison never normalizes file contents. Runtime temporary paths are the only normalized values in command output

Phase A intentionally retains Python command examples in plan output and preset file comments. Changing those bytes belongs to the removal phase, after both implementations have proved parity. Recipes preserve the measured distinction: plan exits 0 with guidance, install exits 2 with guidance on stdout and the refusal on stderr

Swift Argument Parser supplies help and syntax-error presentation. Its executable name, help layout, and syntax-error exit status of 64 differ from argparse's layout and exit status of 2. Registry refusals still exit 2, validation defects exit 1, and diff exits 1 only for differences. Invalid registry loading now reports the readable validator report rather than the Python install entry point's uncaught traceback. Foundation's underlying JSON and I/O error descriptions differ from Python's runtime descriptions. These differences concern parser and runtime diagnostics, not ownership decisions or generated bytes

Preset numeric values use Python's ties-to-even rounding. Decoding keeps the known low bits of all 22-character codes, including values exceeding UInt128. Seeded random output reproduces Python's MT19937, integer seeding, and rejection sampling, including negative integers and integers beyond 64 bits. The Showcase remains unchanged; its behavior beyond the shared vectors is not silently widened by this migration

## Verification

Run `swift build`, `swift test --filter RegistryKitTests`, and `python3 -m unittest discover Tests/RegistryTests` from the repository root. Run both validators and all three Python generators, then verify no generated files changed. `python3 Scripts/check_swift_parity.py` runs the temporary subprocess oracle after a build. `make format` and `make format-check` format and lint the new Swift tool and its tests without rewriting canonical registry source or generated consumers

The fixture provenance and negative cases are described in `Tests/RegistryKitTests/Fixtures/README.md`. Python remains the publishing path until Phase C. `Scripts/capture_previews.py` remains Python after that phase because it automates the pinned simulator captures and has no consumer CLI role
