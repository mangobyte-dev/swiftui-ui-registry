# Swift CLI migration contract

Stage status and phase evidence live in `docs/component-roadmap.md`, Stage 6. This document records the implementation choices and compatibility boundaries for the rewrite

## Running from a clone

```sh
swift run swiftui-registry validate
swift run swiftui-registry search nutrition dashboard --kind block --platform iOS --target-version 26.0
swift run swiftui-registry install button --destination Sources/Feature/Components --plan
swift run swiftui-registry preset decode a13GkaOXWwIF
swift build -c release
```

Consumer commands accept `--registry /absolute/path/to/clone` after the command name. Without it, the local source searches the working directory and its ancestors for `Registry/registry.json`. Published command examples (catalog pages, the website, the Showcase, plan output) spell the tool as `swiftui-registry <command>`; from a clone that is `swift run swiftui-registry <command>`, and a release build lives at `.build/release/swiftui-registry`. Outside a clone the tool resolves the pinned release snapshot described under Resolution and distribution below

## Package boundaries

`RegistryKit` has no dependency on `SwiftUIRegistryFoundations` and imports no SwiftUI. It owns loading, structural validation, resolution, receipts, source comparison, installation, search, preset behavior, the MCP protocol, and all three generators. The executable owns argument parsing and output. The existing foundation target and its source remain design tokens only

The three direct dependencies are `swift-argument-parser` for the real parser exercised by command tests, `swift-dependencies` for replaceable effects, and `swift-snapshot-testing` for inline output and directory snapshots. Their resolved transitive packages are recorded in `Package.resolved`; there are no other direct package dependencies. The pattern was measured from `pointfreeco/pfw` at 854b491

Filesystem access including home expansion, registry selection, console output, line-oriented stdin, UUID generation, and the git merge adapter are dependencies. Tests supply an in-memory filesystem and registry source. The merge integration test selects the live git adapter deliberately. The snapshot manifest and the update-notice stamp read the injected clock (`@Dependency(\.date.now)`), and the network and tar effects (`RegistryDownloader`, `RegistryArchive`, `ReleaseTags`) carry throwing test values, so no test reaches the network by accident

The Showcase retains its codec in Phase A. Its tuning model contains app-only environment switches and remembered color state; importing the entire consumer tool engine only for the codec would couple that private model to installer dependencies. RegistryKit and the unchanged Showcase continue to consume the same pinned vector contract, `Registry/preset_vectors.json` since Phase C; the Showcase test reads it by path and the RegistryKit test resource is byte-checked against it

## Parity boundaries

Owned source, receipt JSON, bases, conflict artifacts, search JSON, and preset theme files preserve the Python bytes. The parity script compared exit status and both output streams; its directory comparison never normalized file contents, and runtime temporary paths were the only normalized values in command output. It was removed with the Python path in Phase C; its last complete run is recorded at `796b399` in the roadmap

The overlap phases intentionally retained Python command examples in plan output and preset file comments; Phase C changed those bytes to `swiftui-registry` commands after both implementations had proved parity, and regenerated every consumer. Recipes preserve the measured distinction: plan exits 0 with guidance, install exits 2 with guidance on stdout and the refusal on stderr

Swift Argument Parser supplies help and syntax-error presentation. Its executable name, help layout, and syntax-error exit status of 64 differ from argparse's layout and exit status of 2. Registry refusals still exit 2, validation defects exit 1, and diff exits 1 only for differences. Invalid registry loading now reports the readable validator report rather than the Python install entry point's uncaught traceback. Foundation's underlying JSON and I/O error descriptions differ from Python's runtime descriptions. These differences concern parser and runtime diagnostics, not ownership decisions or generated bytes

Preset numeric values use Python's ties-to-even rounding. Decoding keeps the known low bits of all 22-character codes, including values exceeding UInt128. Seeded random output reproduces Python's MT19937, integer seeding, and rejection sampling, including negative integers and integers beyond 64 bits. The Showcase remains unchanged; its behavior beyond the shared vectors is not silently widened by this migration

## MCP and generator serialization

`OrderedJSON` preserves insertion order for the website export and MCP responses, including their nested formatted text. It validates parsed input through the existing JSON decoder before retaining object order and number spelling. It is separate from `JSON.rendered`, whose sorted output remains the receipt and search contract. `MCPTools.swift` carries the seven protocol declarations copied from the Python server; the executable does not duplicate them

`RegistryInput` supplies complete lines without waiting for end of input, and `RegistryConsole` is the sole MCP output path. The server delegates to RegistryKit and reloads validated metadata on every registry tool call. Home expansion is a filesystem effect, so in-memory tests can assert a `~/Components` plan without consulting the test runner's home directory

The catalog and manifest generators retained the original templates during parity; Phase C changed only their generated-by header and install command lines. Generator stdout uses pathlib-style lexical path spelling. The site exporter copies image bytes through the filesystem dependency and preserves the six preset descriptions and screenshot selection rules. The generator drift test compares all files and image bytes against the checked-in outputs using an in-memory destination

## Resolution and distribution

`LocalRegistrySource` resolves the registry in a fixed order: the `--registry <path>` override, then a clone enclosing the working directory (the nearest ancestor holding `Registry/registry.json`), then the cached snapshot of the pinned release. The pinned release is `RegistryRelease.version`, the constant the executable reports as `--version` and the MCP server names in `serverInfo`. The snapshot is the GitHub tag archive `https://github.com/mangobyte-dev/swiftui-ui-registry/archive/refs/tags/<version>.tar.gz`, unpacked with `tar --strip-components=1` into `~/Library/Caches/swiftui-registry/registries/<version>/`, beside a `snapshot.json` manifest recording the version, the URL, and the clock's `fetchedAt`

A cache is valid when the manifest names the pinned version and `Registry/registry.json` is present; a valid cache serves every command without a request. `--refresh` downloads the archive again into a staging directory, replaces the cache only after the archive proved to contain a registry, and rewrites the manifest. A failed download or unpack leaves the previous cache untouched, removes the staging directory, and exits 2 with the URL, the cause, and the `--registry` hint. `--refresh` and `install --force` are separate: `--refresh` touches only the cache and the update stamp, `--force` touches only owned source in the destination, and they may be combined. Neither the override nor an enclosing clone is affected by `--refresh`. The fetch is announced on stderr, so MCP stdout stays clean

After a successful `install` or `install --update`, the tool asks the tap `mangobyte-dev/homebrew-tap` for its tags through the GitHub tags API, takes the first tag with the `swiftui-registry-` prefix, and prints `swiftui-registry <version> is available. Run 'brew update && brew upgrade swiftui-registry' to install.` when that differs from the running version, as measured from pfw's `pfw-` tags. Unlike pfw, one request a day is enough: `~/Library/Caches/swiftui-registry/update-check.json` records the clock's `checkedAt` and the latest tag, `--refresh` asks regardless, `--plan` and `--diff` never ask, and any failure is silent and leaves the stamp alone

Distribution follows pfw's release shape: `.github/workflows/release.yml` runs `swift build -c release --arch arm64 --arch x86_64` on `macos-26` when a GitHub release is published and uploads `swiftui-registry-macos-universal.tar.gz` and its `.sha256` to that release with `gh`. `Distribution/homebrew/swiftui-registry.rb` is the formula template for the owner's `mangobyte-dev/homebrew-tap` (`Formula/swiftui-registry.rb`): the owner copies the checksum from the uploaded `.sha256` and tags the tap `swiftui-registry-<version>` so the notice can see the release. The `0.1.0` tag, the GitHub release carrying the universal binary, and the tap (tag `swiftui-registry-0.1.0`) were published on 2026-09-06; `brew install mangobyte-dev/tap/swiftui-registry` is the documented install path, and the snapshot download was verified live from a directory outside any clone with the Homebrew-installed binary

## Command and disk contracts

This table is the compatibility checklist for the rewrite, not a completion claim. Phase implementation and verification evidence belong to the roadmap. The Swift tests under `Tests/RegistryKitTests/` define exact wording and negative cases; the Python originals are in git history before Phase C

| Command | Contract to preserve |
|---|---|
| `validate [item ...]` | Full or scoped dependency-closure validation; exit 0 with `Registry validation passed: full catalog` or scoped wording; exit 1 with the ordered readable defect report |
| `search [query ...] [--kind component\|block\|flow\|recipe] [--platform NAME] [--target-version X.Y] [--format json\|names]` | Every query term matches; name, alias, tag, description ranking and deterministic tie order; the same JSON fields |
| `describe <item> [--format text\|json] [--source]` | The shared `describe_item` payload the MCP tool returns; text lists the usage snippet, accessibility notes, install order, package requirements, and file targets, a recipe reports its native guidance instead, `--source` appends canonical file content, and an unknown item exits 2 |
| `install <item> --destination <dir> [--force\|--update\|--plan\|--diff]` | Dependency-closed preflight, identical skips, collision and ownership refusals, packages and manifest snippets; diff exits 1 for differences, registry refusals exit 2; recipe install exits 2 and recipe plan exits 0 with native guidance |
| `info --destination <dir> [--format text\|json]` | Reads the destination receipt and reports each owned file as up-to-date, modified, or missing against its installed digest, with per-item lines and a summary count; a missing receipt exits 2 like the installer's `--diff` |
| `preset decode <code> [--json]`, `url <code>`, `apply <code> --destination <dir> [--force]`, `resolve <path> [--json]`, `random [--seed N]` | The same code grammar and 22-character limit, shared vectors, seeded output, text and JSON, generated theme bytes, and refusal to overwrite an edited theme |
| `mcp` | Newline-delimited JSON-RPC on stdin/stdout; seven tools, exact structured content and error paths, protocol negotiation for `2025-06-18`, `2025-03-26`, and `2024-11-05`; logs on stderr only |
| `generate catalog`, `generate showcase-manifest`, `generate site-data` | Byte equality for all generated files and copied images, including output cleanup; use the corresponding Python generator's output options |

The MCP tools are `search_items`, `describe_item`, `plan_install`, `diff_item`, `install_item`, `describe_preset`, and `apply_preset`. Every tool must call the same RegistryKit operations as its CLI counterpart. The server reloads validated registry metadata per tool call so edits are visible without restarting. Compare both the wire response and the formatted text nested inside `content`; parsed-object equality alone misses drift

`.swiftui-registry/receipt.json` in the destination uses schema version 1. It records registry identity, item versions and dependencies including every SwiftPM rule, and file ownership with digests and base paths. Bases are `bases/<id>.base`; conflict artifacts are `conflicts/<id>.merge`. Neither artifact may have a `.swift` extension. Verify the exact paths against `Installer.swift` and the Python oracle before changing them

The interoperability proof must install with Python and update with Swift, then install with Swift and update with Python. Diff complete directory trees after the updates, including receipts, bases, conflicts, and the absence of unintended files. Exercise local edits, upstream edits, a clean three-way merge, conflicting edits, and forced cleanup. No normalization is permitted inside file contents

## Verification

Run `swift build`, `swift run swiftui-registry validate`, the three generators, `git diff --exit-code` over the generated paths, and `swift test` from the repository root, then `make format-check`. `swift test` needs `git` on PATH for the merge adapter and Node 22 for the website codec check. The Python oracle and its parity script no longer exist; the byte contracts they proved are pinned by the inline snapshots and captured fixtures under `Tests/RegistryKitTests/`. `SnapshotTests.swift` proves the resolution order, the cache reuse, `--refresh`, the failure paths, the manifest, and the update notice's tags, throttle, and silence through injected effects, plus the live tar extractor and the live downloader over file URLs; the live GitHub paths are exercised only by running the binary outside a clone. `make format` and `make format-check` format and lint the Swift tool and its tests without rewriting canonical registry source or generated consumers

The fixture provenance and negative cases are described in `Tests/RegistryKitTests/Fixtures/README.md`. Phase C removed the Python consumer and publishing path. `Scripts/capture_previews.py` remains Python because it automates the pinned simulator captures and has no consumer CLI role; it lists and validates the items and checks a preset code through the built `swiftui-registry` tool (`--tool`, or a release build from the clone)
