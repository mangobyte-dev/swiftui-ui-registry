## Findings

### 1. Point-Free ergonomics: how their tools earn it

- F1.1 Thin app, fat library, previews import the library. Ep 21 (2018-07-09) canonizes "thin app target containing only `AppDelegate`, fat framework target containing all view controllers / models / styling / utilities, playground importing the framework for live previews"; Ep 22 shows the same at site scale with `PointFreeTestSupport` housing every mock "so playgrounds and tests can share the same controlled world" (PF-1). The registry already has this shape: the Showcase app is a shell over `SwiftUIRegistryShowcasePackage`, and `Examples/TodoCounter` is three UI layers over shared reducers (MEM)
- F1.2 Dependencies as structs of closures with a failing test value. Ep 16 replaces protocol-based DI with "a single `Environment` struct of closure-properties"; Ep 114 ships `WeatherClient.unimplemented` (all fields `fatalError`), "direct ancestor of `swift-dependencies`'s `testValue` enforcement" (PF-2). RegistryKit already injects its effects this way (`registryDownloader`, `registryArchive`, `releaseTags` with throwing test values; MEM). Small composable primitives with controllable effects are the ergonomics, not a large API surface
- F1.3 Compile-time-verified code generation. Ep 55: "save snapshot as a real `.swift` file, the compiler validates it" (PF-3, "Crossover Episodes", row 55), and KH-2 records the same as the load-bearing convention behind their macro playbook. The registry's three generators plus `generatedOutputsMatchCanonicalBytes` are this pattern; a generated Showcase manifest that does not compile fails the build
- F1.4 A skill carries the current API, its arc carries the why. "A skill without its arc is a recipe without a reason. An arc without its skill is history without a deliverable" (PF-3, "How to use this guide"). Skills are structured as frontmatter (`name`, `description`, `license`, `metadata.short-description`), then `## IMPORTANT`, `## Goal`, `## Quick start`, `## API interface`, and `## How to ...` sections with numbered `### Step` subsections; the interface lives under `references/interface/` (PF-4, headings of `pfw-dependencies/SKILL.md` lines 11 to 205)
- F1.5 Five recurring design patterns worth borrowing: free function to struct to protocol to macro; a domain model that survives three rebuilds of Apple's presentation API because the enum layer never depended on it; a five-year delay before shipping shared state rather than break exhaustive testing; performance archaeology measured before it reshaped internals; the same abstraction kept across three implementation substrates (PF-3, "Evolution Patterns"). For the registry: the preset code format is the abstraction that must survive implementation churn, which is why its append-only rule exists (`docs/registry-spec.md`, "Preset codes")

### 2. The knowledge hub's four topics

- F2.1 Polish. The hub's default for a solo iOS 26 app: "Start native, honor every system setting, and add custom motion or effects only where the stock set visibly breaks"; Hudson's 10-minute checklist as the floor (VoiceOver labels, Dynamic Type, 44x44, decorative-image marking, `accessibilityInputLabels()`), every animation gated behind Reduce Motion, Panferova privileged on the platform surface, private API refused, and "A prototype reads as a prototype mostly because it skipped the free, standard settings, not because it lacked a bespoke effect" (KH-1, "The hub's default"). All seven experts agree that native components and system colors carry accessibility and dark mode for free (KH-1, "Where they agree")
- F2.2 Workflow. Sarno's tooling ladder starts with code snippets and reaches file templates "only after the architecture is frozen"; the hub privileges Point Free on "without lowering quality" because compile-time verification is the strongest guard, keeps debug tooling behind `#if DEBUG`, and keeps a human review gate on every generated change (KH-2, "The hub's default"). Every expert agrees: "Automate the predictable", "Earn the tool first", "Use AI for grunt work, not for judgment" (KH-2, "Where they agree")
- F2.3 AI-assisted development. Hudson's skill shape is "a small SKILL.md entry point plus lazy-loaded reference files" that does not reteach what the model knows and targets "edge cases, soft deprecations, and the mistakes LLMs actually make"; Zablocki ships persistent rule files so output fits the codebase's conventions; Point Free's guardrail is type-level, "wrong code fails to compile"; and "API hallucination" is named as the unsolved problem, so "verify any unfamiliar API against the SDK before you trust agent output" (KH-3, positions and "The hub's default")
- F2.4 Composition. Structural identity is load-bearing (ternary or inert modifier over `if`/`else`), repeated modifier chains are extracted once into a `ViewModifier`, a `View` extension, or a style protocol, Aether mirrors Apple's `ButtonStyle` and `LabelStyle` shape, and `onGeometryChange` is preferred over `GeometryReader` (KH-4, "Where they agree" and the validity table). The validity table also records that `Style` (SwiftUI, introduced 26.0) is now a first-class protocol family, which the registry's `.registry` styles sit on
- F2.5 New APIs no expert has covered, in the areas Stage 7 touches: `accessibilityPrefersCrossFadeTransitions` (26.4), `CrossFadeNavigationTransition` (27.0), `backgroundExtensionEffect` (26.0), `GlassEffectTransition` (26.0), `ScrollEdgeEffectStyle` (26.0) (KH-1, "New APIs in this topic's area with no expert position"). None is needed by a registry item; the sidebar recipe and the Showcase may use `backgroundExtensionEffect` where the HIG asks for it (F3.9)

### 3. Apple's Human Interface Guidelines for iOS, iPadOS, and Liquid Glass

- F3.1 Two layers. "Liquid Glass forms a distinct functional layer for controls and navigation elements - like tab bars and sidebars - that floats above the content layer"; "Don't use Liquid Glass in the content layer"; "Use Liquid Glass effects sparingly"; "Only use clear Liquid Glass for components that appear over visually rich backgrounds"; the four standard materials (ultra-thin, thin, regular, thick) are for "visual distinction" within the content layer, with label vibrancy levels label, secondaryLabel, tertiaryLabel, quaternaryLabel and fill levels fill, secondaryFill, tertiaryFill (HIG-M, "Liquid Glass" and "iOS, iPadOS"). The decision tree adds the WWDC26 251 framing, "the UI layer, which serves as the global navigation, and the content layer", and rules "Badge or pill on a content card: Not glass" and "Sheet background: System handles it; don't override `presentationBackground`" (LG-1, "The two layers" and "Judgment calls")
- F3.2 Color. "Avoid using the same color to mean different things"; "If you define a custom color, make sure to supply light and dark variants, and an increased contrast option for each variant"; "Even if your app ships in a single appearance mode, provide both light and dark colors to support Liquid Glass adaptivity"; "Avoid hard-coding system color values"; "Avoid redefining the semantic meanings of dynamic system colors" (HIG-C, "Best practices" and "System colors"). On glass: "Apply color sparingly ... To emphasize primary actions, apply color to the background rather than to symbols or text ... Refrain from adding color to the background of multiple controls" (HIG-C, "Liquid Glass color"). iOS defines two background sets (system and grouped), each with primary, secondary, and tertiary levels, and the foreground colors label, secondaryLabel, tertiaryLabel, quaternaryLabel, placeholderText, separator, opaqueSeparator, and link (HIG-C, "iOS, iPadOS"). Twelve named system colors (red through brown) and six system grays are specified (HIG-C, "Specifications")
- F3.3 Typography. Default 17 pt, minimum 11 pt on iOS and iPadOS; "avoid Ultralight, Thin, and Light font weights"; "Minimize the number of typefaces you use"; the text styles are "a typographic hierarchy" that "scale proportionately when people change the system's text size"; "Consider using the built-in text styles"; the developer note says use `default` for the system font and `serif` for New York through the `Design` constants; SF Pro Rounded exists "to coordinate text with the appearance of soft or rounded UI elements"; a custom font must "implement the same behaviors" as Dynamic Type; "Keep text truncation to a minimum as font size increases" (HIG-T, "Ensuring legibility", "Conveying hierarchy", "Using system fonts", "Using custom fonts", "Supporting Dynamic Type"). The Large (default) table runs Large Title 34/41 Regular down to Caption 2 11/13 Regular, eleven styles (HIG-T, "Large (default)"). SwiftUI's `fontDesign(_:)` was introduced in 16.1, `fontWidth(_:)` in 16.0, `monospacedDigit()` in 15.0, `Font.custom` in 14.0 (KH-5)
- F3.4 Layout. "Differentiate controls from content. Take advantage of the Liquid Glass material ... Instead of a background, use a scroll edge effect"; "Extend content to fill the screen or window"; "When your content doesn't span the full window, use a background extension view"; "Avoid full-width buttons" on iOS (HIG-L, "Best practices", "Visual hierarchy", "iOS"). On iPadOS: windows resize freely, "defer switching to a compact view for as long as possible", "Test your layout at common system-provided sizes" (halves, thirds, quadrants), and "Consider a convertible tab bar for adaptive navigation" through `sidebarAdaptable` (HIG-L, "iPadOS"). Size classes: every listed iPad is regular width and regular height in both orientations; iPhone 17 is compact width, regular height in portrait and compact in both in landscape (HIG-L, "iOS, iPadOS device size classes")
- F3.5 Control sizes and contrast. iOS and iPadOS: default control size 44x44 pt, minimum 28x28 pt; contrast follows WCAG Level AA ratios in Accessibility Inspector (HIG-A, "Offer sufficiently sized controls" and "Strive to meet color contrast minimum standards")
- F3.6 iPad design. "Take advantage of the large display to elevate the content people care about, minimizing modal interfaces and full-screen transitions"; "Let people use Multi-Touch gestures, a physical keyboard or trackpad, or Apple Pencil"; "Adapt seamlessly to appearance changes - like device orientation, multitasking modes, Dark Mode, and Dynamic Type" (HIG-P, "Best practices")
- F3.7 Pointer. iPadOS has three content effects: highlight (bar buttons, tab bars, segmented controls by default), lift (app icons), hover (custom scale, tint, shadow). "Use highlight for a small element that has a transparent background. Use lift for a small element that has an opaque background. Use hover for large elements"; "Prefer the system-provided pointer appearances for standard buttons and text-entry areas"; hit-region padding "about 12 points ... around elements that include a bezel; for elements without a bezel ... about 24 points"; "Create contiguous hit regions for custom bar buttons"; "Avoid creating gratuitous pointer and content effects" (HIG-PD, "Pointer shape and content effects", "Standard pointers and effects", "Customizing pointers"). SwiftUI: `hoverEffect` introduced 13.4, `defaultHoverEffect` 18.0, `hoverEffectDisabled` available (KH-5)
- F3.8 Keyboard. "Support Full Keyboard Access when possible", and the boxed note: "Although iPadOS supports keyboard navigation in text fields, text views, and sidebars ... avoid supporting keyboard navigation for controls, such as buttons, segmented controls, and switches. Instead, let people use Full Keyboard Access" (HIG-K, "Best practices"). Focus: "Pressing the Tab key moves focus among focus groups"; "Pressing an arrow key supports a directional focus interaction ... limited to navigation among items in the same focus group"; the halo effect is the focus ring (HIG-F, "iPadOS"). SwiftUI `focusable` was introduced in 17.0 and `keyboardShortcut` is available (KH-5)
- F3.9 Split views and sidebars. "Prefer using a split view in a regular - not a compact - environment"; iPadOS split views have two or three panes and must "Account for narrow, compact, and intermediate window widths" (HIG-SV, "iOS" and "iPadOS"). "Consider using a tab bar first"; `sidebarAdaptable` lets an app open with either and switch; "To display a sidebar only, use NavigationSplitView"; "Extend visually rich content beneath the sidebar ... by applying a background extension effect" (HIG-SB, "Best practices" and "iOS, iPadOS"). `NavigationSplitView` introduced 16.0, `backgroundExtensionEffect` 26.0, `tabViewBottomAccessory` 26.0 (KH-5)

### 4. Design systems that survived: what they name and what they leave to the platform

- F4.1 Apple names semantics, never values: two background sets by three levels, four label levels, separators, placeholder, link, twelve named colors, six grays (F3.2); eleven text styles (F3.3); four standard materials plus Liquid Glass (F3.1); regular and compact size classes (F3.4); default and minimum control sizes (F3.5). It leaves nothing to a vendor because it is the platform; a design system on iOS that renames these creates the "confusing" duplication the color page warns about
- F4.2 shadcn names token pairs and studio options. - F4.3 Radix names a scale and six theme knobs. The 12-step scale: steps 1 and 2 are app and subtle backgrounds, 3 to 5 are UI element background, hovered, and active or selected, 6 to 8 are subtle borders, element borders and focus rings, hovered borders, 9 and 10 are solid backgrounds and hovered solids, 11 and 12 are low- and high-contrast text; "Steps 11 and 12 - which are designed for text - are guaranteed to Lc 60 and Lc 90 APCA contrast ratio on top of a step 2 background from the same scale" (RX-1). Radix Themes exposes `accentColor`, `grayColor`, `radius`, `scaling`, `appearance`, and `panelBackground` (RX-2)
- F4.4 Material names roles and containers. `ColorScheme` carries primary, secondary, tertiary, and error each with on-, container, and on-container roles, plus surface, surfaceDim, surfaceBright, surfaceContainerLowest, Low, default, High, Highest, onSurface, onSurfaceVariant, outline, outlineVariant, shadow, scrim, inverseSurface, inversePrimary, and surfaceTint, and `ColorScheme.fromSeed` will "Generate a ColorScheme derived from the given seedColor" (MD-1). The type scale is fifteen roles, display, headline, title, body, label in large, medium, small, from 57/64 to 11/16 (MD-2)
- F4.5 The shared vocabulary across the three, in the registry's terms: a fill always names its "on" color (shadcn `-foreground`, Material `on-`, the registry's `onAccent`); surfaces come in levels (Material's five containers, Radix steps 1 to 5, Apple's three background levels); borders are a separate low-contrast step (Radix 6 to 8, shadcn `border` and `input`, Material `outlineVariant`); a radius scale is one knob (shadcn 5, Radix `radius`, Apple's continuous corners); an accent is picked from a fixed palette (Radix and shadcn hues, Apple's twelve colors); a chart palette is separate from the accent (shadcn chart-1 to 5, ADA-1 law 17); and a neutral tint under everything is its own choice (shadcn base color, Radix `grayColor`, Material's neutral palettes). What every one of them leaves to the platform on iOS: fonts and icons (F4.2), and depth: Apple specifies materials and no shadow tokens for content (F3.1), Material specifies elevation with `shadow` and `surfaceTint` (MD-1), and the award apps use neither strokes nor shadows but a luminance step (F5.1)

### 5. What award-winning SwiftUI apps keep

- F5.1 Law 1: "One lifted surface on a quiet ground; depth is fill and elevation, never a stroke", with Any Distance's stroke count at zero and Ice Cubes' surface "6-8 hex points above the canvas" (ADA-1, "The laws", Law 1 and move 9). This contradicts the registry's `registrySurface`, which fills `theme.surface` and strokes `theme.border` at `borderWidth` (REG, `RegistryTheme.swift`, `RegistrySurfaceModifier`). shadcn strokes its cards with `border` (SH-2) and the HIG does not forbid a hairline (HIG-L names "separator lines" among the ways to group). Recorded as a conflict and resolved in D3 and D4 by keeping the token and letting a theme set the border to nothing
- F5.2 Law 2: one accent "spent once per screen, only on what you can act on", which is the same rule as the HIG's "Refrain from adding color to the background of multiple controls" (F3.2). Law 3: "The number is the design: big value, tiny muted label, tabular digits, animated on change". Law 5: "One committed identity, applied to every surface with no exception". Law 6: every empty state is a drawn screen that "never says no data". Law 7: motion is "a tiny fixed vocabulary tied to a data change, and it honors Reduce Motion", with press feedback at scale 0.95 to 0.97 (move 24). Law 8: "Native bones; go custom only where the platform cannot pay" (ADA-1). Law 8 is this registry's thesis
- F5.3 Typography by role: "Reserve one editorial display face for the headline and the hero number. Use the system face for everything else" (ADA-1, move 11), and "Set every number in tabular or monospaced digits" (move 12). Together with HIG-T's "Minimize the number of typefaces", a theme's typography is one design choice for display text, the system face for the rest, and tabular digits wherever a value can change
- F5.4 What no winner does: stroked cards, a dashboard of many small stat tiles, accent as decoration on chrome, a bare spinner or the words "no data", mixed radii, a confirm dialog on a reversible action, a hand-built tab bar or a control that imitates a native one (ADA-1, "What NOT to do")

### 8. The pain point: consistent, beautiful design systems on iOS, and the ecosystem that does not exist

Added at the owner's request on 2026-09-06. Reddit could not be read: the search tool reports that reddit.com blocks its crawler and the site's JSON endpoints returned no data to this session, so no Reddit thread is cited here

- F8.1 Drift is the pain everyone names first. "Every SwiftUI project ends up rebuilding the same primitives: styled buttons, form inputs with validation states, card containers, modals with proper focus handling. Then the design system inevitably drifts because there's no single source of truth for spacing, radius, color, or elevation. Six months in, half the app uses one theme and half uses whatever the busy dev shipped that sprint" (OW-4, 2026-07-01). "As SwiftUI apps grow, UI consistency becomes fragile", with the symptoms "slightly different padding values", "inconsistent corner radii", "random colors hardcoded everywhere", "dark mode bugs", "accessibility issues", "painful rebranding work" (OW-5). "Building a design system to support one product is not easy - it has to be robust and flexible at the same time for scalability" (OW-8, 2019). The owner's own app was measured against the award grammar and found to break it through "many surfaces, scattered color, mixed radii, and chrome that competes with the food" (ADA-1, headline finding)
- F8.2 Coding agents make the drift worse. "If you're building with an AI coding agent, the drift problem is worse, not better. Ask Claude, Cursor, or Codex to 'add a settings screen' three separate times and you'll get three different paddings, three different corner radii, and a button style that quietly forked itself somewhere around commit 40. Agents are great at writing plausible SwiftUI and bad at remembering what the rest of your app already decided" (OW-4, 2026-07-07). This is the same diagnosis the hub records as Zablocki's "average code" and Hudson's unsolved API hallucination (F2.3), and the registry's answer is metadata an agent reads instead of invents: the item `usage` snippets, the MCP server, and the skills of slice 9
- F8.3 Apple ships the mechanism but not the contract. "On Android, Jetpack Compose gives us MaterialTheme out of the box. On iOS? We have to build our own"; without one, "developers often resort to hardcoded values scattered across views, or passing theme objects through initializers"; and "SwiftUI's Environment system is the equivalent of Compose's CompositionLocal" (OW-6). Apple names the semantics (F4.1) and provides the environment, and leaves the set-up-once theme value to each team. `RegistryTheme` in the environment with `registryTheme(_:)` at the root is that missing contract (F7.2)
- F8.4 The obvious SwiftUI shortcut for tokens is a trap. Extending `Color` with design-system statics means "Using SwiftUI's built-in colors alongside design system colors makes them visually indistinguishable at call sites, increasing the risk of accidental misuse", and because `Color` is a `ShapeStyle`, "`Color.babyBlue.secondary`" type-checks although "our design system doesn't define any secondary baby blue variant", so "this capability becomes a liability"; Apple's `ForegroundStyle` route "is unfortunately quite limited" (OW-7). The registry's tokens live on a theme value in the environment rather than as `Color` statics, which is the shape OW-7 argues for
- F8.5 The ecosystem has been tried and it stalls. shadcn's Swift port `swiftcn-ui` was announced on Hacker News on 2023-09-24 and received 2 points and no comments (OW-11); it holds 146 stars, its last push was 2024-04-24, and its README opens with "We are looking for a maintainer for this repository" (OW-10); the awesome-shadcn-ui list names it as the only Swift port (OW-13); a second port, `Dicky019/swiftcn`, was created on 2026-02-05 and has 3 stars (OW-10). Two corporate design systems published as SwiftUI packages were archived in 2025: Kiwi.com's Orbit (147 stars, last push 2025-05-07) and Orange's ODS (179 open issues) (OW-10). The maintained survivors are a package of controls (ComponentsKit, 182 stars, pushed 2026-06-24, "A library with UIKit and SwiftUI components to build iOS apps faster") and an AI-recipe catalog that funds itself with a services upsell (ShipSwift, 2,983 stars in nine months, "Need a custom app built? We do that too", from $5,000 (1,543 KWD at the 2026-09-06 rate from open.er-api.com)) (OW-10). A 2026 comparison of eleven libraries ranks them by last commit and warns "An unmaintained UI dependency becomes your problem at the next iOS release" and "'Last commit' is the column that matters most" (OW-9). Sameness is the web's version of the same pain: shadcn's own changelog says "somewhere along the way, all apps started looking the same" (SH-1, `2025-12-shadcn-create.mdx`)
- F8.6 Why no dominant solution exists was already recorded on 2026-08-29 and still holds: "SwiftUI already supplies strong controls, product UI is domain-specific, source copying complicates updates, Xcode project integration is less uniform than web file systems, and visual taste is harder to standardize than control behavior" (ARC, item 3); the answer to sameness is to "Keep foundations semantic and small, make higher-level source editable, and publish multiple domain compositions rather than one global skin" (ARC, item 15)
- F8.7 The demand is recurring and unanswered. The question "Is there a shadcn for swiftui?" was asked on Threads on 2025-05-24 (OW-12), the DesignFoundation author asked it of himself in July 2026 and answered with a package (OW-4), and the owner's own words on 2026-08-31 were that shadcn/ui has no SwiftUI equivalent "and it's a shame, because SwiftUI and React are both declarative" (MEM-2). Each answer so far has been a package of new controls, which is the shape that goes unmaintained (F8.5) and the shape the hub's experts warn against when Apple already supplies the control (F2.1, KH-4)

## Decisions

Each decision names the findings it rests on and the slice it binds. The roadmap's Stage 7 section carries the same decisions in short form; that copy is the one that binds

- D1 Parity (slices 3 and 4). A shadcn row becomes a `recipe` when Apple supplies the presentation or the whole value is a native modifier choice (the value gate in `docs/registry-spec.md`), a `component` only when iOS has no native control or the treatment is reusable across items, and a `block` only when it composes registry items. No registry treatment applies Liquid Glass, because every registry item is content (F3.1, LG-1); a treatment that promotes a control into floating chrome is documented as a recipe using the system glass button styles (`docs/philosophy.md`, "Liquid Glass boundaries"). Rows that exist only because the web lacks a platform primitive (icon libraries, font loading, hover-only affordances, CSS variant matrices) are dispositioned "not applicable to iOS" with the reason drawn from F4.2 and F4.5
- D2 iPad (slice 5). Every item and block is captured at regular width on the iPad Pro 13-inch and checked against the size-class facts in F3.4. Pointer: verify each item on the iPad simulator; keep the system pointer effects for standard controls (F3.7), add `hoverEffect(.highlight)` or `.lift` only where a registry style has removed the default and the HIG rule for small transparent or small opaque elements applies, use `hover` for large elements, and never add a decorative effect. Keyboard: no custom keyboard navigation for buttons, toggles, or segmented controls; text fields, lists, and sidebars keep their native focus; Full Keyboard Access is the path (F3.8), and the Showcase UI suite runs on the iPad destination. Navigation: the existing `sidebar` recipe gains the `sidebarAdaptable` tab style as the HIG's first choice and keeps `NavigationSplitView` for a sidebar-only layout with `backgroundExtensionEffect` under it (F3.9, F7.1); a sidebar block is built only if a composition of registry items passes the value gate, and the default is that it does not, because the `Preview02` wall already renders a sidebar as content
- D3 MANGO (slice 6). MANGO is a `RegistryTheme` preset and a preset code, with a typography choice expressed as a `Font.Design` applied once at the root (`.rounded`, to match its generous radii, F3.3 and F5.3), tabular digits on every value that can change (F5.3), no stroke (border opacity zero) with depth from a surface luminance step (F5.1, F4.5), one accent spent on the primary action (F5.2), light and dark pairs for every custom color (F3.2), and a motion vocabulary taken from Emil Kowalski's skill: critically damped springs at response 0.4 by default, 0.8 damping only after a gesture with momentum, press feedback on the button style, cross-fades under Reduce Motion (F6.3, F5.2). The template document walks a team through the Layers order: domain, conceptual model, surface (F6.1), and names the third-party skill as the example of extending the system. Whether a theme becomes an item kind remains the slice's decision, and the research recommends no new kind: a preset code already round-trips through the tool, the Showcase, the website, and the MCP server, `RegistryTheme+App.swift` is by contract "not a registry item" (`docs/registry-spec.md`, "Preset codes"), and shadcn's `registry:theme` items exist because CSS variables must be installed as files, which a Swift value does not need (F4.2, F7.2). MANGO's one or two customized items are owned copies tracked by the receipt, the same path `Examples/TodoCounter` proved (MEM)
- D4 The Create studio (slice 7). New knobs, each with the finding that admits it and the one that shapes it: background color as an optional custom pair with the system background as the default (F3.2, F4.5); surface elevation as a ladder of surface levels (lowest, low, default, high) implemented as luminance steps, and no shadow tokens, because Apple specifies materials for content and the winners use neither strokes nor shadows (F3.1, F4.5, F5.1); foreground and secondary foreground as an optional custom pair with the system label hierarchy as the default and the secondary derived by opacity unless set (F3.2); font design as one of default, rounded, serif, monospaced applied through `fontDesign(_:)` (F3.3); a custom font family only in the Swift export and the theme package, never in the code, and only with the Dynamic Type behavior the HIG requires (F3.3); the size scale is Apple's eleven text styles rendered in the chosen design, and the studio adds no custom point sizes because a custom scale forfeits Dynamic Type (F3.3, F2.1); spacing and radius keep their fields and gain named density presets (compact, regular, generous) as bundles of the existing metrics, the iOS reading of shadcn's eight styles (F4.2); a chart palette choice, accent-derived or a fixed hue set, so the chart can leave the accent alone (F7.3, F4.5); a `warning` semantic only if two items adopt it in the same slice, since foundations add a token only with two consumers (`AGENTS.md`); light and dark pairs for every custom color, in the 24-plus-24-bit shape the accent already uses (F3.2, F7.4). Every new field is appended after the custom accent block under version letter `b`, with `Registry/preset_vectors.json`, the RegistryKit codec, the website codec, and the Showcase codec updated together, and version `a` codes keep decoding (F7.4, F1.5)
- D5 Website hardening (slice 8). Playwright under `Website/` drives search and every Create control in Chromium and in WebKit with an iPhone profile, asserts a clean console, and encodes the two 2026-09-06 crashes as regression tests: opening the ⌘K dialog on every page, and dragging a slider for longer than ten seconds without a `SecurityError` (F7.5). CI runs it on every push
- D6 Skills (slice 9). The three skills follow the Point-Free file shape (frontmatter, `Goal`, `Quick start`, `API interface`, `How to` sections with numbered steps, references under `references/`; F1.4) at Hudson's weight (a small entry point, lazy references, no reteaching of SwiftUI the model knows; F2.3), each `How to` carrying its why as a link into `docs/philosophy.md` or `docs/architecture.md` so the skill is never "a recipe without a reason" (F1.4), every snippet quoted from the foundations `.swiftinterface`, the generated catalog, or an item's `usage` field because API hallucination is unsolved (F2.3), and the authoring skill teaching the conceptual model (item, kind, dependency, receipt, code) before the surface (F6.1)
- D7 Developer experience (cross-cutting). The tool keeps Point-Free's ergonomics as its measure: small composable commands, effects behind controllable dependencies with failing test values, previews and tests as the product, and generated output the compiler verifies (F1.1 to F1.3). Swift Algorithms enters only as a tool dependency, only in a slice that shows a hand-written loop it replaces in RegistryKit, and never in registry source (F6.2). A missing shadcn CLI or MCP affordance gets a Swift equivalent only when slice 4 shows the value is real, per the roadmap's own wording
- D8 The pain points are the brief for MANGO's template and the skills (slices 6 and 9). Each recorded pain maps to the registry mechanism that answers it, and the MANGO template document and the three skills state that mapping in their `Goal`: drift (F8.1) is answered by one `RegistryTheme` set once at the root and tokens read from the environment, never from `Color` statics (F8.3, F8.4); agent drift (F8.2) is answered by the `usage` snippets, the MCP server, and the skills, which carry what the rest of the app already decided; the missing MaterialTheme (F8.3) is answered by the theme contract plus a preset code that survives copy and paste; maintenance risk (F8.5) is answered by source ownership, the narrow foundations package with a pinned range, receipts, `--diff`, and `--update`; sameness (F8.5, F8.6) is answered by the Create studio and MANGO as the worked example of a brand built on the same items. The website's home page may carry the same table, but that is copy for the owner to place and not a Stage 7 slice
